# Table UX — Implementation Plan (Package C)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Player statistics respect the active filters, and any index page can select rows and bulk-edit them.

**Architecture:** Three strands. First, `players.status_value` is promoted from a free-form string to a `player_statuses` lookup table with per-locale names, matching `categories`. Second, the four stat blocks stop being hardcoded `DB::table` queries and route through the same filter helper the list uses. Third, the row-selection logic already living inside `Players/Index.vue` is extracted into a reusable composable and paired with a bulk-edit modal, backed by one guarded `bulkUpdate` endpoint per resource.

**Tech Stack:** Laravel 13, PHP 8.3, Inertia 2 + Vue 3, Tailwind 3, SQLite, PHPUnit 12.

Spec: `docs/superpowers/specs/2026-07-20-post-testing-enhancements-design.md` (Package C).

## Global Constraints

- SQLite only. No `ALTER TABLE ... ADD CONSTRAINT`; enforce in the model and Form Request.
- PHPUnit with `#[Test]` attributes, `RefreshDatabase`, extending `Tests\TestCase`. **No `PlayerFactory` exists** — build players with `Player::create([...])` and a unique `membership_id`.
- Run tests with `php artisan test --filter=<TestClass>`; style with `./vendor/bin/pint <paths>`.
- Flash messages are **i18n keys**, never English. `FlashTranslationTest` fails the build otherwise. Add every new key to all three of `resources/js/i18n/{en,fr,ar}.json`.
- Bulk endpoints must be permission-gated exactly like the single-record update they stand in for, and wrapped in a transaction.

## Decisions taken

**`status_value` becomes a lookup table.** Chosen over keeping the free-form string because status is currently untranslatable (hardcoded Arabic literals in a Vue `<select>` at `PlayerForm.vue:291-299`), imported players can carry arbitrary strings that pollute `statusStats`, and the allowed list is duplicated in the frontend rather than managed in Settings.

**`status_value` is kept, not dropped.** The new `status_id` FK is added alongside it and backfilled. The old column stays as a safety net for one release — imported junk values that match no known status would otherwise be silently destroyed. Dropping it is a follow-up once the data is confirmed clean.

**Each doughnut excludes its own dimension.** The category chart applies every active filter *except* `category_id`. Otherwise selecting a category collapses that chart to a single 100% slice and the user can no longer switch category from it, breaking the existing click-a-slice-to-filter interaction.

**No shared DataTable.** All 55 index pages hand-roll their `<table>`; rewriting them is out of scope. A `useBulkSelection()` composable plus two small components let any page opt in.

### Task 5: Extract `useBulkSelection`

**Files:** `resources/js/Composables/useBulkSelection.js`, `Players/Index.vue:120-130`

Lift the existing `selected` / `pageIds` / `allSelected` / `toggleAll` / `toggleOne` logic verbatim, plus clear-on-filter-change:

```js
import { computed, ref, watch } from 'vue';

/**
 * Row selection for an index page. Extracted from Players/Index.vue so any
 * page can opt in without a shared table component.
 */
export function useBulkSelection(rows, resetSignal = null) {
    const selected = ref([]);

    const pageIds = computed(() => (rows.value ?? []).map((r) => r.id));
    const allSelected = computed(() =>
        pageIds.value.length > 0 && pageIds.value.every((id) => selected.value.includes(id)));

    function toggleAll() {
        selected.value = allSelected.value ? [] : [...pageIds.value];
    }

    function toggleOne(id) {
        const at = selected.value.indexOf(id);
        at === -1 ? selected.value.push(id) : selected.value.splice(at, 1);
    }

    function clear() {
        selected.value = [];
    }

    // A filter change replaces the rows; keeping stale ids would silently
    // apply a bulk action to records no longer on screen.
    if (resetSignal) {
        watch(resetSignal, clear, { deep: true });
    }

    return { selected, pageIds, allSelected, toggleAll, toggleOne, clear };
}
```

Rewire `Players/Index.vue` to use it. Behaviour must be identical — the existing archive/restore/delete bulk actions keep working.

- [ ] **Step 2: Implement**

```php
class BulkUpdatePlayersRequest extends FormRequest
{
    /** Only these may be set in bulk. An allow-list, never a blocklist. */
    public const FIELDS = ['category_id', 'position_id', 'status_id', 'branches'];

    public function rules(): array
    {
        return [
            'ids' => ['required', 'array', 'min:1', 'max:500'],
            'ids.*' => ['integer', 'exists:players,id'],
            'field' => ['required', Rule::in(self::FIELDS)],
            'mode' => ['nullable', Rule::in(['replace', 'attach', 'detach'])],
            'value' => ['present'],
        ];
    }
}
```

`bulkUpdate()` validates `value` against the chosen field (each `*_id` must exist in its table; `branches` must be an array of branch ids), then applies it inside a transaction. `branches` uses `sync` / `syncWithoutDetaching` / `detach` per `mode`. Flash `flash.players_updated` with the count.

The 500-row cap and the allow-list are the safety rails: without them a crafted request could rewrite any column on every player.
